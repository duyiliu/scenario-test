# 生成与维护业务场景

仅在 `status=installed` 且项目文件可读时进入。日常使用**不再安装、不自动升级**。结构探测不等于 doctor PASS；遇到版本锁或文件异常时先诊断，正常编写无需每次重新初始化。

1. 使用探测脚本返回的**同一个项目**的路径读取：`AI_SCENARIO_PROMPT.md`、`SCENARIO_PATTERNS.md`、`scenario-test-capabilities.json`、`scenario.config.js`、项目场景文件。不要使用全局缓存中的 DSL 规则或别的项目的文件。存在能力疑问时，执行 `node <cli> capabilities --json`（`<cli>` 为项目内 CLI），并以项目实际支持能力为准。
2. 只定位本次业务目标涉及的 Controller、OpenAPI、前端 API、接口文档或已有测试；有功能名称和入口就直接工作，缺少定位依据时询问**最小的必要信息**。不要遍历整个业务仓库生成所有场景。
3. 严格按项目内 AI 规则先得到功能卡片与场景矩阵；有不确定字段/枚举/认证/响应时列待确认项。按有证据的验证路径编写或修改 `scenario.config.js` 与 `scenarios/`，保留已有场景、ID 和团队改动，不修改业务代码、公共运行时或项目依赖。
4. 对矩阵中每条候选行为显式决策，再动手：
   - **复用**：已有场景已触发目标条件，且断言能证明业务结果（含跨接口场景）。
   - **增强**：已有场景触发了条件但断言不足（只有 200/字段存在，或缺少后置状态验证）→ **在原文件原场景补断言**。若新候选与已有场景的路径与成功条件等价，一律合并进已有场景，不得并存两个等价场景，也不得删除/重命名已有场景或 ID（除非用户明确要求）。
   - **新建**：独立且重要的业务行为，已有场景没有可信验证。
   - **暂不创建**：与已有等价、低价值技术分支（日志/缓存命中/纯实现细节）；说明取舍，不得据此跳过有证据的高风险行为。
   - **待确认**：响应码/字段/枚举/数据准备方式未在源码或契约中确认时，只列待确认项，**不为它创建场景**（也不要塞进已有场景文件）；禁止写死猜测的 `status: 500`、错误码或字段名来凑场景。同一规则的等价输入合并；不同权限、状态转移或关键不变量即使共用接口也分别验证。
   写操作还要检查是否存在防重复提交、唯一约束或幂等要求；有证据时评估「重复提交不产生第二条记录」并给出可观察的后置验证，证据不足则列待确认。期望的错误响应必须来自全局异常处理或统一响应结构等真实证据。
   功能卡片中由源码确认的每条关键规则（含状态前置条件、等级冲突、重复提交）都必须在矩阵里出现并给出上述决策，不得静默略过。修改已有文件时，`registerScenario` 的场景 ID 必须原样保留；新增行为另起文件或使用新 ID。
   总结里输出「规则 → 决策（新建/复用/增强/待确认）」逐条映射，便于核对是否有遗漏。
5. 用项目本身支持的 DSL 编排独立场景，保持断言可验证、测试数据隔离与精确清理。代码证据不足时不要猜测路径、状态码、响应字段或写入值。
   - 针对本次涉及的唯一性、幂等、状态变更等关键风险，除成功或拒绝断言外，须通过有源码或接口契约依据的可观察查询验证对应副作用，例如重复新增被拒后记录仍唯一且原记录未被覆盖、拒绝状态变更后状态保持原值。已有场景缺少该关键断言时优先补强；没有可用查询路径则明确列出验证缺口，不虚构接口或数据。本要求用于场景设计，不授权实际调用接口，也不要求扩展无关场景。
6. 静态检查所改文件及现有引用关系。需要时运行 `doctor`（不调用业务 HTTP），但**不要**擅自执行 `run`、`serve`、登录或任何业务接口调用。
7. 总结场景矩阵、修改文件、待确认问题和可选的执行命令；用户要求真正执行时才切换到 `execute.md`。

项目内 `AI_SCENARIO_PROMPT.md` 优先于本文件对 DSL 细节的描述；这里是全局工作流，不是 DSL 的另一份事实来源。
